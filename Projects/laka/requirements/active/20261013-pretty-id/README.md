# Pretty ID — SALFA × YOOY 参考整合原型

## 使用
直接打开 delivery.html，无需后端或安装。index.html 是多文件维护入口；css/style.css、js/app.js、js/engine.js 随包保留。本地预览：http://localhost:8765/delivery.html。

## 参考与设计
只使用用户提供的 SALFA 与 YOOY 截图。原创酒红/香槟金界面、SVG冠翼徽章、权益卡、奖励预览。保留之前确认的返回链路和删除当前 ID/次数展示的调整。资料卡仅保留昵称、财富和SVIP等级。无竞品广播、音乐或支付系统。

## 两种兑换途径
财富等级：原SALFA A/B/C；SVIP：YOOY SS/S/A/B/C。入口显式切换，按所选途径匹配、检查资格和发放该类别奖励，不将两个竞品的类别优先级混为一套。号码归属唯一、次数、记录仍全局共享。

### 已确认并启用的截图模板
财富C：LV80 BAA、BBB、ABA、AAAA；LV90 AAA、ABB；LV95 AB、AA；LV100 A。BAA=ABB、BBB=AAA，因此对应三位结构在LV80可解锁。
SVIP SS：SVIP5 AB、AA。
配置集中维护于 js/engine.js。字母代表重复结构而非固定输入；只允许纯数字或纯字母，统一大写。最大长度来自已配置模板，目前4。

## 原型假设，生产前须确认
- 财富和SVIP显式选择；如果两种资格都满足，奖励依据所选途径，而非跨体系比较。
- 高等级继承低等级配置；默认LV100、SVIP0且有效、剩余2次。
- 两种途径共享兑换次数；原图未提供各途径次数表。
- SVIP5 AA/AB沿用纯数字或纯英文字母的输入约束。
- 原财富类奖励为永久头像框和聊天气泡；SS示意永久头像框和身份徽章，第二项名称/类型无法从图中确认。
- SVIP有效性通过测试面板模拟。过期只阻止未使用权益，不自动收回已兑换ID；不模拟年底定时任务。
- 修改后旧号仍保留归属直到重置，实际释放策略待确认。

## 页面与状态
首页→等级奖励→返回首页；规则返回实际来源并恢复滚动。输入和已选分类保留。
校验→确认→重新校验→原子更新号码、次数、类别奖励、记录。禁止连续确认造成重复扣减；同类别只发一次奖励。
空输入、非法输入、模板不匹配、等级不足、SVIP过期、已占用、次数不足、请求失败、超时、恢复重试均有反馈。
localStorage保存Mock状态；不写真实业务数据。单HTML与多文件入口共享同域状态。

## 字段与验证
状态：level、svip、svipActive、route、remaining、current、owned、rewards、records；记录包含operationId、route、entitlement、input、pattern、category、level。无真实接口或外发埋点。
逻辑测试：8组通过，包含原财富规则、精确结构、非法输入、占用、次数、幂等、奖励去重；SVIP门槛/过期/两途径隔离，确认前权益过期不产生更新。
浏览器已验证：LV1+SVIP5兑换88成功；SVIP过期拒绝89；财富途径兑换8888成功；分类切换、SS奖励预览、两途径等级规则、来源页返回、删除的ID区块不恢复、字母小写转大写、超时和恢复重试、测试重置。375/390px未发现横向溢出，控制台无错误或警告。未确认的配置不能认定已通过验收。
