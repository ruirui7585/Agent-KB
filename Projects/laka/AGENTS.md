## 1. 文件目的

本文件是 Laka 项目的统一 AI 执行协议。

适用于能够读取本项目目录或已获得本文件内容的 AI 工作环境，包括：

* Codex；
* ChatGPT Work；
* ChatGPT Chat；
* Claude Code；
* Cursor；
* 其他本地或云端 Agent。

Laka 是一个持续运营、持续迭代的长期项目，每周会产生新的产品需求。

所有新需求都必须继承 Laka 已有的：

* 产品背景；
* 公共业务规则；
* 历史产品决策；
* 当前需求状态；
* 真实产品 UI；
* 当前有效的高保真 UI 基线（包括可作为设计参考的历史 HTML 页面）。

不得要求用户重复提供已经存在于项目文件中的内容。

本文件负责定义“AI 应该如何工作以及到哪里读取信息”，不负责保存完整业务背景、完整历史需求或全部 UI 细节。

## 2. 语言与命名规范

### 2.1 文档语言

项目文档采用以下语言规则：

* 产品背景、业务规则、PRD、决策原因、验收标准：以中文为主；
* 文件名、目录名、状态值、字段名、代码标识、接口字段：使用英文；
* App 前台界面文案：默认使用英文；
* 必要时在英文术语首次出现时补充中文解释；
* 不为了“方便模型理解”强制把所有文档翻译成英文。

AI 必须能够理解中文业务规则，不得因为文档以中文编写而降低执行完整性。

### 2.2 文件与目录命名

文件名和目录名必须：

* 使用小写英文；
* 单词之间使用连字符 `-`；
* 不使用空格；
* 不使用中文目录名；
* 不使用 `new`、`latest`、`final-final` 等无明确版本意义的名称。

固定公共文件保留约定的大写名称：

```text
AGENTS.md
PROJECT_CONTEXT.md
DECISIONS.md
REQUIREMENTS_INDEX.md
CHATGPT_CONTEXT.md
UI_SYSTEM.md
SCREEN_SPEC.md
README.md
PRD.md
```

## 3. 项目根目录识别

Laka 项目会在多台电脑上使用，本地绝对路径可能不同。

当前已知合法路径：

```text
家庭电脑：
/Users/judy/Agent/Projects/laka

公司电脑：
/Users/shilv/Agent-Workspace/Projects/laka
```

以上路径属于同一个 Laka 项目在不同设备上的本地副本。

不得将其中任意一个绝对路径写成唯一有效路径。

### 3.1 PROJECT_ROOT

执行任务时，将当前工作环境中已经打开的 Laka 根目录定义为：

```text
PROJECT_ROOT
```

项目根目录应满足：

* 当前目录或其父级目录名为 `laka`；
* 根目录存在 `AGENTS.md`；
* 根目录存在或预期存在 `PROJECT_CONTEXT.md`；
* 根目录存在或预期存在 `requirements/`；
* 根目录存在或预期存在 `ui/`。

在终端环境中，应优先通过以下方式确认：

```bash
pwd
```

不得仅根据用户名、历史路径或预设绝对路径判断当前环境。

### 3.2 相对路径原则

所有项目内部引用必须优先使用相对于 `PROJECT_ROOT` 的路径。

正确示例：

```text
PROJECT_CONTEXT.md
DECISIONS.md
REQUIREMENTS_INDEX.md
ui/UI_SYSTEM.md
ui/screens/im-chat/baseline.html
requirements/active/
requirements/archive/
```

禁止在项目正式文件中硬编码：

```text
/Users/judy/...
/Users/shilv/...
```

只有执行本机命令或用户明确指定外部文件时，才可以临时使用绝对路径。

不得因为某个历史绝对路径不存在，就在该路径下自动创建另一份 Laka 项目。

## 4. 环境读取边界

### 4.1 本地 Agent

当 Codex、Work 或其他本地 Agent 已经打开 `PROJECT_ROOT` 时，应读取并遵循本文件。

### 4.2 网页版或普通 ChatGPT Chat

如果当前聊天无法访问本地文件系统：

* 不得声称已经读取本地路径；
* 应使用用户上传或添加到项目中的文件；
* 应优先读取 `CHATGPT_CONTEXT.md` 和当前需求文件；
* 不得仅凭本地路径名称推测文件内容。

`CHATGPT_CONTEXT.md` 是提供给 ChatGPT 项目的上下文汇总镜像，不是独立事实源。

## 6. 文件职责

### `AGENTS.md`

定义：

* 执行流程；
* 文件读取顺序；
* 修改权限；
* 交付标准；
* 验证和归档规则。

### `PROJECT_CONTEXT.md`

保存所有需求默认继承的长期公共事实，例如：

* 产品定位；
* 用户角色；
* 产品模块；
* 商业模式；
* 平台级业务规则；
* 核心术语；
* 重要业务数据口径。

### `DECISIONS.md`

保存经过用户确认、未来仍可能被复用或错误推翻的重要产品决策及原因。

不用于保存完整历史需求。

### `REQUIREMENTS_INDEX.md`

作为需求总台账，保存：

* 当前需求；
* 需求优先级；
* 文档状态；
* 产品状态；
* 关联页面；
* 当前目录；
* 归档目录；
* 阻塞和待确认问题。

### `CHATGPT_CONTEXT.md`

汇总以下内容，供无法直接读取本地目录的 ChatGPT 项目使用：

* `PROJECT_CONTEXT.md` 的核心信息；
* 当前需求索引；
* 当前有效的重要决策；
* UI 公共规则和核心页面索引。

不得只更新 `CHATGPT_CONTEXT.md` 而不更新正式源文件。

### `ui/`

保存 Laka 当前产品的真实 UI 基线、页面说明和公共 UI 规则。

### `requirements/`

保存每次正式需求的完整增量资料和最终交付物。

## 7. 信息优先级

当信息发生冲突时，按以下优先级处理：

1. 用户在当前任务中的明确指令；
2. 当前需求最新有效的 `README.md` 和 `PRD.md`；
3. 用户明确提供并说明为当前版本的产品截图或 HTML；
4. 对应页面的 `baseline.html`、`reference.png` 和 `SCREEN_SPEC.md`；
5. `PROJECT_CONTEXT.md`；
6. `DECISIONS.md` 中状态为 `Confirmed` 的决策；
7. `REQUIREMENTS_INDEX.md`；
8. 历史需求和归档文件；
9. AI 自身推测。

发现冲突时：

* 使用高优先级信息；
* 不得静默混用两套规则；
* 在交付说明中指出冲突；
* 不得把一次临时修改自动升级成公共规则；
* 不得用归档需求覆盖当前版本。

## 8. 任务开始前的读取规则

### 8.1 所有正式需求必须读取

```text
AGENTS.md
PROJECT_CONTEXT.md
REQUIREMENTS_INDEX.md
```

并根据当前任务在 `DECISIONS.md` 中检索相关决策。

如果需求目录已经存在，还必须读取：

```text
requirements/active/<requirement>/README.md
requirements/active/<requirement>/PRD.md
```

### 8.2 UI 任务必须额外读取

```text
ui/UI_SYSTEM.md
ui/references/reference-index.md
assets/asset-manifest.md
ui/screens/<screen>/baseline.html
ui/screens/<screen>/reference.png
ui/screens/<screen>/SCREEN_SPEC.md
```

其中：

* `ui/references/reference-index.md` 用于识别正式版截图、主参考、辅助状态、重复截图和禁止继承的问题；
* `assets/asset-manifest.md` 用于识别正式素材、线上截图参考、临时素材、缺失正式素材和禁止复用素材。

不得只查看页面截图而跳过截图索引。

涉及宫殿背景、底部导航、货币、VIP、Relationship、徽章或其他品牌素材时，不得跳过素材清单。

读取已有 `baseline.html` 仅用于继承当前真实 UI，不代表默认需要生成新的 HTML。

如果找不到对应页面，应依次检索：

```text
ui/screens/
requirements/active/
requirements/archive/
assets/
```

### 8.3 历史需求读取条件

仅在以下情况读取归档需求：

* 用户明确要求参考历史需求；
* 当前需求属于历史需求二期；
* 当前需求与历史功能高度相似；
* 需要追溯某个重要决策；
* 当前有效文件明确引用历史需求。

归档文件不得默认视为当前规则。

### 8.4 竞品监控任务

当任务涉及竞品池、竞品新版本、新功能、新产品、市场数据、1v1 社交或语音房竞品分析时，必须额外读取：

```text
agents/competitor-analysis/AGENT.md
agents/competitor-analysis/competitor-pool.md
agents/competitor-analysis/monitoring-backlog.md
agents/competitor-analysis/state/monitoring-state.json
```

竞品监控结果统一保存在：

```text
agents/competitor-analysis/reports/
```

每次执行只分析自上次检查后发生的实质变化。未发现实质变化的产品记录“已检查、无重要变化”，不得为了凑满三个产品重复输出旧信息。

## 9. 正式需求判断

满足以下任一条件时，视为正式需求：

* 需要输出正式 PRD；
* 需要输出前台静态高保真 UI、后台静态线框或统一 HTML 评审原型；
* 需要新增或调整业务规则；
* 需要设计前端交互；
* 需要设计后台功能；
* 需要设计接口、状态或数据逻辑；
* 需要提供开发或测试验收标准；
* 需要交付给设计、开发、测试或运营执行。

以下情况默认不创建正式需求目录：

* 单句文案优化；
* 单个概念解释；
* 临时问题咨询；
* 尚未形成交付目标的探索讨论；
* 纯头脑风暴。

当讨论进入正式方案或交付阶段时，再创建需求目录。

## 10. 正式需求目录

正式需求创建在：

```text
requirements/active/
```

目录命名格式：

```text
YYYYMMDD-english-requirement-name
```

示例：

```text
requirements/active/20260712-wishlist-gift/
requirements/active/20260715-message-request/
```

涉及前台或后台 UI 的正式需求最低结构：

```text
requirements/active/<requirement>/
├── README.md
├── PRD.md
├── index.html
├── css/
│   └── style.css
├── js/
│   └── app.js
├── assets/
└── annotations.json
```

没有专属资源时，可以不创建空的 `assets/` 子目录；不得创建空 CSS、JavaScript 或注释文件充数。

`index.html` 是唯一评审入口。CSS、JavaScript、图片和其他资源必须使用相对路径，并随完整需求目录一起交付。不得把前台和后台拆成两个独立 HTML 链接，也不得用分别导出的 PNG 代替统一评审入口。

当同一需求同时涉及前台和运营后台时，`index.html` 使用一级 Tab 在 `App 前台` 与 `运营后台` 之间切换；只涉及一端时不得保留空 Tab。多页面或多状态使用对应 Tab 内的二级页面导航，仍保持同一个 HTML 链接。

纯后台规则、数据、接口或其他不需要可视化的需求可以不创建 HTML，只交付声明范围内的文档和结构化说明。统一 HTML 是静态评审原型，不是生产代码；只有用户明确要求可交互原型或前端实现时，才增加完整业务交互或工程实现。

## 11. 修改前执行规则

开始修改前，必须先输出简短计划，包括：

* 当前任务目标；
* 需求类型；
* 涉及的业务模块；
* 涉及的页面；
* 准备读取的文件；
* 准备新增或修改的文件；
* 是否会修改公共上下文；
* 是否会修改 UI 基线。

输出计划后直接继续执行，不需要等待用户再次确认。

以下情况必须先获得明确授权：

* 删除正式文件；
* 批量移动或重构目录；
* 覆盖无法恢复的内容；
* 修改与当前需求无关的 UI；
* 将 AI 建议写入公共业务规则；
* 修改未经用户确认的平台级事实；
* 操作其他项目或项目外关键文件。

用户在当前任务中已经明确授权时，不重复询问。

## 12. UI 事实源

### 12.1 核心原则

已有产品页面必须基于实际 Laka 产品页面进行增量修改。

不得凭空重新设计已有核心页面。

已有核心页面包括但不限于：

* 1v1 IM 聊天页面；
* 首页或 For You 页面；
* 用户主页；
* 会话列表；
* 私密内容页面；
* 守护关系页面；
* CP 关系页面；
* 充值或收银台页面；
* 语音房页面。

### 12.2 UI 事实源优先级

1. 用户当前明确提供的真实产品截图或 HTML；
2. `ui/screens/<screen>/baseline.html`；
3. `ui/screens/<screen>/reference.png`；
4. `ui/screens/<screen>/SCREEN_SPEC.md`；
5. 当前需求中的已确认原型；
6. 历史需求中的已确认原型；
7. `ui/UI_SYSTEM.md`。

### 12.3 reference.png 定义

`reference.png` 必须是：

* 当前真实产品截图；
* 或用户明确确认可以作为当前产品视觉依据的截图。

不得使用 AI 自行生成的原型截图冒充真实产品截图。

### 12.4 baseline.html 定义

`baseline.html` 表示当前可复用的产品 UI 基线。

`baseline.html` 是公共产品 UI 事实源，不是当前需求的评审入口，也不能替代需求目录中的统一 `index.html`。

它不是：

* 任意探索方案；
* 第一版需求原型；
* 尚未确认的未来版本；
* 临时活动页面。

## 13. AI 自行创建 UI 的边界

AI 可以自行创建：

* 当前产品不存在的全新页面；
* 新功能组件；
* 新弹窗；
* 新浮层；
* 新 Banner；
* 新增交互状态；
* 探索阶段的临时方案。

自行创建时必须：

* 遵循 `ui/UI_SYSTEM.md`；
* 延续 Laka 的既有视觉风格；
* 保持相似的信息密度；
* 使用当前产品已有的组件语言；
* 不改变整体设计风格；
* 明确标记未经确认的假设；
* 不得声称自行创建的页面是当前线上真实页面。

如果新功能需要放在聊天页、首页、主页等已有基础页面中：

* 必须使用实际产品基础页面；
* 不得从空白画布重新构建一个近似页面；
* 不得因为缺少局部信息而重做整个页面。

---

## 14. 缺少实际产品页面时

如果需要修改已有核心页面，但找不到当前截图、HTML 或有效基线：

1. 先搜索全部 UI 文件；
2. 搜索当前需求；
3. 搜索归档需求；
4. 搜索项目已有图片和资源；
5. 可以先设计局部新增组件；
6. 局部方案必须标记为 `Provisional UI`；
7. 不得将临时方案升级为 `baseline.html`；
8. 最终交付前必须获得实际产品页面依据。

不得用“AI 自己认为合理”的页面替代已有产品事实。

---

## 15. UI 增量修改流程

已有页面的需求采用：

```text
读取真实 UI 基线
→ 在当前需求目录建立统一 HTML 评审入口
→ 在 App 前台 Tab 中完成静态高保真 UI
→ 如涉及运营后台，先确认字段表，再完成运营后台 Tab 的静态黑白线框
→ 保留未涉及区域
→ 完成 PRD、字段表与 HTML 一致性验证
→ 根据产品状态决定是否升级 baseline
```

统一评审 HTML 默认只实现评审所需的 Tab、页面、状态和注释切换。用户明确要求可交互原型或前端代码时，才增加保存、发布、审批、接口请求等业务交互及对应验证。

除非用户明确要求，否则不得：

* 删除原有 UI；
* 移动原有模块；
* 改变已有组件顺序；
* 修改与当前需求无关的交互；
* 替换真实产品素材；
* 重做整个页面；
* 简化其他已有功能；
* 擅自修改背景、导航、资料卡或输入区域；
* 直接覆盖公共 `baseline.html`。

新增 UI 必须说明：

* 展示位置；
* 层级；
* 尺寸；
* 展示条件；
* 触发条件；
* 点击行为；
* 状态变化；
* 与原有 UI 的关系；
* 是否遮挡现有内容。

## 16. 默认交付物

### 16.1 前端用户可见需求

默认交付：

```text
README.md
PRD.md
index.html
css/style.css
js/app.js
annotations.json
```

必要时增加：

```text
assets/
```

无特殊说明时，Laka 项目所有需要 UI 或原型产出的正式需求，均通过一个 `index.html` 评审入口交付。前台用户可见页面在 `App 前台` Tab 中以静态高保真形式展示。

静态高保真描述视觉质量，不代表必须实现完整业务交互。默认只实现评审导航、Tab、页面和状态切换；用户明确提出可交互原型、React/Vite 实现或前端代码时，才切换为对应的业务交互或工程实现。

### 16.2 后台、数据、接口或纯规则需求

默认交付：

```text
README.md
PRD.md
```

以上默认仅适用于不需要 UI 可视化的后台、数据、接口或纯规则需求。只要需要运营后台可视化，就必须增加统一 `index.html` 评审包，并在其中使用 `运营后台` Tab；同时涉及前台时，与 `App 前台` Tab 共用同一入口。

根据需求增加：

* 字段表；
* 状态表；
* 数据口径；
* 接口约定；
* 测试场景；
* Excel 或其他结构化文件。

如果需求涉及运营后台配置，必须先在 `PRD.md` 中建立后台字段表。字段表是后台字段的唯一事实源，每个字段至少定义：

* 稳定字段 ID；
* 所属页面和分组；
* 展示顺序；
* 字段名称和业务含义；
* 控件类型；
* 是否必填、默认值、取值范围、格式或单位；
* 显示、联动和禁用条件；
* 查看及编辑权限；
* 可编辑状态；
* 生效时间和生效方式；
* 异常、冲突和错误提示；
* `Confirmed`、`Proposed` 或 `TBD` 确认状态。

后台字段默认按照运营人员完成任务的顺序组织，不得直接照搬数据库字段顺序、接口返回顺序或 PRD 中的出现顺序。列表、筛选、新建、编辑、详情和审批页面分别定义字段；联动字段紧跟控制字段；系统 ID、创建时间、更新人和操作记录等只读信息独立放入系统信息区域。

制作运营后台可视化前，必须集中请求 PM 确认字段是否齐全、字段含义、分组、顺序和解释。涉及金额、权限、审批、结算、隐私、状态流转或其他高风险规则的未确认字段不得由 AI 补成产品事实。

需要运营后台可视化时，在统一 `index.html` 的 `运营后台` Tab 中展示静态黑白线框；不需要可视化时只交付 PRD、字段表及适用的状态、数据、接口和测试说明。后台线框不得默认为高保真视觉或完整业务交互。

后台线框中的每个字段必须显示与字段表一致的字段 ID，例如 `F01`、`F02`。同一视图内必须提供常驻字段解释区，至少说明字段名称、用途、填写或选择规则、默认值、取值限制、联动条件、权限和生效方式；注释器不能替代这份固定字段解释。

字段变化时必须先更新字段表，再同步更新 `index.html`。不得只修改可视化结果。交付前必须检查字段表和 `index.html` 是否存在缺失字段、多余字段、编号不一致、名称不一致、分组或顺序不一致、缺少解释等问题。

## 19. 竞品截图参考要求

创建或修改 `App 前台` Tab 中的静态高保真 UI 前，先判断当前需求是否已有明确、有效的 UI 参考。`运营后台` Tab 的黑白线框默认不触发竞品视觉调研，除非后台信息架构或控件模式缺少可靠依据，或用户明确要求调研。

以下情况无需搜索竞品：

* 用户当前提供了明确的截图、原型图或 HTML；
* 蓝湖存在当前有效设计稿；
* 对应页面已有有效的 `baseline.html`、`reference.png`、`SCREEN_SPEC.md`；
* 当前需求已有用户确认的原型；
* 现有参考足以确定布局、展示位置、信息层级和主要交互状态。

以下情况必须搜索竞品：

* 没有参考图，只有文字需求；
* 现有参考无法支持高保真实现；
* 新增组件、弹窗、付费状态或异常状态没有参考；
* 属于 Laka 尚未出现的全新页面或交互；
* 用户明确要求进行竞品调研。

如果只有局部 UI 缺少参考，仅搜索缺失的组件或状态，无需重新调研整个页面。

触发搜索后：

1. 至少查找 3 个相关产品；
2. 将截图、预览或有效链接发给用户查看；
3. 简要说明可参考部分和与 Laka 的差异；
4. 用户看过后再继续高保真 UI。

竞品只用于补充布局、信息层级和交互细节，不得覆盖 Laka 真实 UI 基线、已确认设计、业务规则或品牌风格。

## 20. 统一 HTML 评审原型规范

涉及 UI 或原型产出的正式需求默认适用本节。统一评审包必须：

* 使用 `index.html` 作为唯一入口；
* 将视觉样式保存到 `css/style.css`，将 Tab、页面、状态和注释切换保存到 `js/app.js`；
* 图片、图标、字体和其他资源按需保存在 `assets/`；
* 使用相对路径，不依赖交付目录外的本机绝对路径；
* 完整需求目录可本地预览、跨设备迁移并通过同一个远端链接访问；
* 同时涉及前台和后台时使用 `App 前台`、`运营后台` 两个一级 Tab；只涉及一端时不显示无效 Tab；
* 多页面或多状态使用对应一级 Tab 内的二级导航，不创建第二个独立 HTML 入口；
* `App 前台` Tab 使用 Laka 当前 UI 基线完成静态高保真展示，并在 `440 × 956` 主视口及适用的窄、宽视口验证；
* `运营后台` Tab 使用黑、白、灰完成静态线框，清楚展示信息架构、字段分组、字段顺序、控件形式、状态和操作位置；
* 后台字段解释常驻在对应线框同一视图，不要求评审者跳转到另一文件才能理解字段；
* 默认只实现评审所需的 Tab、页面、状态和注释切换；保存、发布、审批、接口请求等业务交互只有在用户明确要求时才实现；
* 保留用户未要求修改的现有 UI；
* App 前台文案默认使用英文，产品说明、字段解释和 PRD 默认使用中文；
* 不出现空白页、失效关键资源、无效 Tab 或无法查看的关键状态。

统一评审页沿用项目约定的注释评审能力。注释工具必须可关闭或收起，不得改变原 UI，不得拦截非注释模式下的评审导航；后台固定字段解释不得只存在于注释器中。

如果当前 `baseline.html` 已有稳定结构，应延续原结构，不得为个人偏好强制重写。统一需求评审 `index.html` 只有在页面已正式采用并符合公共基线升级条件时，才可以更新对应 `baseline.html`。

当正式源文件发生变化后同步更新。

## 23. 需求完成与归档

用户选择的默认规则是：

> PRD 和应交付的统一 HTML 评审原型完成后自动归档；不需要 UI 可视化的后台、数据、接口或纯规则需求，以声明的结构化交付物完成为归档依据。

但“完成”必须同时满足质量条件。

### 23.1 前端需求归档条件

1. `README.md` 已完成；
2. `PRD.md` 已完成；
3. `index.html` 及其 CSS、JavaScript、资源和注释文件已完成；同时涉及前台和后台时两个一级 Tab 均已完成；
4. PRD 与 UI 交付物一致；
5. UI 交付物已完成可执行范围内的检查；
6. 验收标准已覆盖；
7. 不存在阻止交付的未解决问题；
8. 用户未明确表示仍在讨论或当前不是最终版；
9. `REQUIREMENTS_INDEX.md` 已更新；
10. 公共知识提炼已经完成。

不得因为第一版 PRD 和第一版 UI 已生成就立即归档。

### 23.2 非前端需求归档条件

后台、数据、接口或纯规则需求，在声明的正式交付物完成并通过检查后归档。需要运营后台可视化时必须完成统一 `index.html` 中的 `运营后台` Tab；不需要 UI 可视化时不强制创建 HTML。

### 23.3 归档含义

归档表示：

* 当前需求文档包已经完成；
* 当前需求不再占用 `active/` 工作区。

归档不必然表示：

* 已开发；
* 已上线；
* 已成为当前产品 UI；
* 已升级公共基线。

产品实际状态必须单独记录。

### 23.4 归档路径

```text
requirements/archive/YYYY/YYYYMMDD-english-requirement-name/
```

归档时：

* 移动完整需求目录；
* 保留 PRD、`index.html`、CSS、JavaScript、资源和注释文件；
* 不要求为前台或后台额外保存原型 PNG；
* 更新 `REQUIREMENTS_INDEX.md`；
* 不删除正式资料；
* 不把完整需求复制进 `DECISIONS.md`；
* 不把归档文件默认视为当前规则。

## 25. 统一 HTML 评审原型验证

本节适用于所有生成或修改统一 HTML 评审原型、可交互原型或前端实现的任务。

交付前尽可能检查：

### 文件

* 文件存在且非空；
* CSS 生效；
* JavaScript 可加载；
* 资源路径有效；
* 页面可直接打开。
* `index.html` 是唯一评审入口；
* CSS、JavaScript、图片和其他资源使用相对路径；
* 完整交付目录可迁移，不依赖本机绝对路径。

### 页面

* 无空白页；
* 移动端尺寸合理；
* 主要区域完整；
* 无关键元素溢出；
* 无重要内容被遮挡；
* 视觉风格未偏离 Laka。
* 需求同时涉及前台和后台时，`App 前台` 与 `运营后台` Tab 均存在且内容正确；
* 需求只涉及一端时，不存在空白或无效 Tab；
* 后台线框保持黑白静态表达，字段解释清晰可读。

### 交互

* 一级 Tab、二级页面导航和必要状态切换有效；
* 注释评审能力可用且不会破坏原 UI；
* 用户明确要求实现的业务按钮、弹窗、返回和状态操作可用；
* 未要求业务交互的静态界面不得被误报为已完成交互验证。

### 基线

* 未删除无关组件；
* 未修改无关 UI；
* 未改变用户未要求调整的组件顺序；
* 新功能位置符合需求；
* 新功能不遮挡主要内容。

### 逻辑

* PRD、后台字段表与 `index.html` 一致；
* 用户角色一致；
* 状态一致；
* 权限一致；
* 边界条件一致；
* 界面文案与交互一致。
* 后台字段 ID、名称、分组、顺序、控件和解释与字段表一致；
* HTML 中不存在字段表未定义的后台字段；
* 字段表中不存在应展示但未出现在 HTML 的字段；
* `Proposed` 和 `TBD` 字段未被表现为已确认事实。

### 右侧预览自动打开

每次完成统一评审 HTML 的新建、修改、优化或修复后，必须自动将当前需求唯一有效的 `index.html` 在右侧内置浏览器中打开，供用户直接查看，不需要等待用户再次确认。

执行要求：

1. 必须在文件保存并完成当前可执行的验证后，再打开最终有效版本；
2. 如果右侧浏览器已经打开同一个 `index.html`，应自动刷新该页面；
3. 如果尚未打开，应使用当前有效文件路径或本地预览 URL 新建页面，并将右侧浏览器显示给用户；
4. 不得只在回复中提供链接而不执行打开或刷新操作；
5. 不得打开旧版本、归档版本、临时副本或与当前需求无关的 HTML；
6. 如果页面依赖本地服务，应先启动可用的本地预览服务，再打开对应 URL，并保持服务运行以便用户查看；
7. 最终回复必须说明右侧页面是“已打开”还是“已刷新”，并同时提供可点击的文件路径或预览 URL；
8. 如果当前环境不支持右侧内置浏览器，或打开操作失败，不得声称已经打开；必须说明具体限制，并提供当前有效 HTML 的可点击路径。

如果当前环境不能实际运行 HTML：

* 不得声称已经完成浏览器运行验证；
* 应执行静态检查；
* 明确说明尚未实际验证的项目。

## 27. AI 假设规则

AI 可以对非关键细节采用合理默认值继续执行，但必须：

* 优先使用项目已有上下文；
* 采用风险最低的方案；

* 不把假设写成确认事实；

* 收费；
* 主播收益；
* 用户权限；
* 合规；
* 数据删除；
* 状态机；
* 历史数据；
* 版本兼容；
* 核心页面结构；
* 永久公共规则。
