## 3. 主业务流程

```text
[进入 Recharge Rewards (默认 Monthly)]
  → [服务端下发当前周期: 累计金额 / 下一档金额 / 剩余金额 / 进度% / 倒计时 / 档位与奖励列表]
  → [用户切换 Daily / Weekly / Monthly 触发拉取对应周期独立数据]
  → [达标档位显示 Receive]
      ├─ 点击 Receive（自动发放类：VIP/头像框/座驾/称号/金币/勋章）
      │    → [服务端校验档位资格与幂等锁] → [发放资产并更新为 Claimed (Received)] + [Toast: You have successfully claimed the rewards!]
      └─ 点击 Receive（人工发放类：靓号模板/定制礼物/首页大屏曝光）
           → [生成人工履约记录并更新为 Pending Fulfillment] → [展示 Contact Ops 引导]
```

## 4. 核心业务规则（`Confirmed` vs `TBD`）

1. **R1 三周期统计与联动**（`Confirmed`）
   - 条件 / 逻辑 / 结果：支持 `Daily`、`Weekly`、`Monthly`，默认选中 `Monthly`。一笔成功 USD 充值同时计入所有符合时间范围的激活周期；各周期维护独立累计金额、档位列表、奖励内容与倒计时，按自然周期重置。
2. **R2 动态充值进度条**（`Confirmed` 展示结构 / 含 `P0-1` 数值冲突）
   - 条件 / 逻辑 / 结果：展示当前累计充值、下一档金额、距离下一档差额；进度公式 `min(当前累计 / 下一档金额, 1) * 100%`；单笔跨多档直接更新到最新未达标下一档；**下一档金额必须以服务端返回为准，H5 不自行推算**；达到最高档时显示 `100%` 完成态并隐藏“下一档金额”与“剩余金额”。
3. **R3 奖励类型与排序**（`Confirmed`）
   - 条件 / 逻辑 / 结果：支持 9 类奖励（VIP 等级、头像框、座驾、称号、金币、靓号模板、勋章、定制礼物、身份曝光 Banner/首页大屏）；单档支持配置多个不定数量奖励；H5 严格按服务端接口返回顺序渲染。
4. **R4 五大领取状态机**（`Confirmed` + 含 `P1-1` 混合发奖缺口）
   - 条件 / 逻辑 / 结果：档位状态含 `Locked`（未达标禁用）、`Available`（可领，展示 `Receive`）、`Claimed`（已领，展示 `Received`）、`Expired`（已过期禁用）、`Pending Fulfillment`（已领待人工发放，引导联系运营）。领取成功统一提示：`You have successfully claimed the rewards!`。
5. **R5 靓号模板特殊规则**（`Confirmed` 文案 / 范围 `TBD`）
   - 条件 / 逻辑 / 结果：靓号模板不等于最终靓号 ID，实际 ID 由运营协助分配；若不同档位获得多个靓号模板，仅可兑换一个；`Rules` 页固定展示：`If you receive multiple Custom ID template rewards from different tiers, you can redeem only one.`。具体“跨周期还是单周期仅限一次”待确认（`TBD-05`）。
6. **R6 底部 `Recharge Now` 与 `Rules` 跳转**（`Confirmed`）
   - 条件 / 逻辑 / 结果：`Recharge Now` 吸底固定，点击跳转端内充值收银台；充值完成后返回活动页需重新拉取服务端最新进度与档位状态；`Rules` 位于右上角，进入独立规则页。

## 5. 状态流转与 7 维边界矩阵（必查防漏）

### 5.1 档位状态流转表

| 当前状态 | 触发事件 | 前置校验 | 目标状态 | 页面可见变化与可用/禁用操作 |
|---|---|---|---|---|
| `Locked` | 用户完成 USD 充值且达标 | 周期未结束、累计金额 ≥ 档位门槛 | `Available` | 按钮由禁用 `Locked` 变为高亮 `Receive` |
| `Available` | 点击 `Receive`（全自动奖励） | 周期未结束、幂等未领、无风控拦截 | `Claimed` | 按钮变为 `Received`，弹出成功 Toast |
| `Available` | 点击 `Receive`（含人工履约奖励） | 同上 | `Pending Fulfillment` | 按钮变为禁用 `Pending`，显示 `Contact Ops` 引导 |
| `Available` | 周期倒计时归零 | 周期结束且奖励未领取 | `Expired` | 按钮变为禁用 `Expired`，不可点击（`TBD-04` 确认） |
| `Pending Fulfillment` | 运营后台核销发奖完成 | 后台标记“已发放” | `Claimed` (`Proposed`) | 按钮/状态变为 `Received`（待确认是否回写 `Claimed`） |

### 5.2 高频边界核查表（7 维必查）

| 边界维度 | 具体场景 | 处理规则 / 兜底方案 | 状态 |
|---|---|---|---|
| **权限变更/受限** | 账号封禁、支付风控冻结、游客/未登录态打开活动链接 | 封禁或风控用户禁止点击 `Receive`，报错提示并拦截发奖；充值跳转需校验登录态（`Proposed`）。 | `TBD` |
| **时序/时区/跨日** | 自然日/周/月重置基准时区；`23:59:55` 发起支付、`00:00:08` 回调成功归属哪一周期 | 需明确统一平台时区（如 `UTC+0` 或 `UTC+3`）；建议以**支付成功回调时间（或订单创建时间，二选一锁定）**为准，并禁止跨周期重置瞬间倒计时误差导致的超领。 | `TBD` |
| **并发与幂等** | 用户弱网连点两次 `Receive`；多设备同账号同时领取；领奖后返回页未刷新 | 服务端按 `userId + cycleInstanceId + tierId` 加分布式唯一锁实现幂等，重复请求直接返回已有结果且不重复发金币/记录；切前台（`onResume`）自动刷新状态。 | `Proposed` |
| **失败/中断/回滚** | ① 请求超时结果未知；② Apple/Google 支付退款或拒付（Chargeback） | ① 前端超时提示刷新状态，禁止直接乐观置为 `Claimed`；② 退款冲正必须联动扣减对应周期累计充值额；若奖励未领则退回 `Locked`，若已发消耗品/曝光权需定义负向追缴或黑名单策略。 | `TBD` |
| **存量与配置级联** | 周期进行中运营修改档位金额、替换奖励或下架某档位；旧版本客户端访问 | 建议周期开启后**锁定核心档位门槛**（或仅允许下周期生效），已生成领奖记录/已解锁档位按触发时快照履约；旧版本不识别新 `rewardType` 时降级通用礼物图标与文字。 | `TBD` |
| **极限值与混排** | 累计充值 `$0`、单笔跨全档、`>$30,000`；多奖励单档长英文或阿语 RTL 混排；某周期后台未配置档位 | 达最高档隐藏下一档与剩余金额并置 `100%`；货币统一千分位 USD；长名称最多两行省略；无配置周期 Tab 隐藏不渲染空页（`Proposed`）。 | `Proposed` |
| **版本兼容** | iOS/Android 内嵌 H5 WebView 桥接差异（返回、跳转 `Recharge`、联系运营入口） | 需复用现有客户端 JSBridge 跳充值页与客服通道；未知奖励类型有默认图标兜底，不崩溃。 | `Confirmed` |

## 8. 可测试验收标准（Acceptance Criteria）

1. **AC-01 默认展示与周期独立切换**：Given 用户已登录进入 `Recharge Rewards`，When 页面完成首屏加载，Then 默认激活 `Monthly` Tab 并渲染服务端返回的累计 USD、倒计时、进度条与档位列表；切换 `Daily / Weekly` 时，金额、进度、倒计时与档位同步更新且互不干扰。
2. **AC-02 单笔跨档与满档 100% 隐藏下一档**：Given 用户当前周期累计低于最高档，When 单笔充值金额一次跨越 2 个档位，Then 当前累计、所有新达标档位状态（变 `Available`）与新的下一档目标即时更新；若已达最高档，Then 进度条显示 `100%` 且不再展示“下一档金额”与“剩余金额”。
3. **AC-03 自动 vs 人工发奖与成功反馈**：Given 某档位处于 `Available`，When 点击 `Receive`：若仅含自动奖励，Then 资产到账、按钮更新为 `Received` 并弹出 `You have successfully claimed the rewards!`；若包含人工发放奖励，Then 状态更新为 `Pending Fulfillment` 并展现 `Contact Ops` 引导。
4. **AC-04 规则页与多靓号模板声明**：Given 用户在 `Recharge Rewards` 点击右上角 `Rules`，When 进入 `Rules` 页，Then 完整显示 5 条规则及固定英文文案 `If you receive multiple Custom ID template rewards from different tiers, you can redeem only one.`。
5. **AC-05 连点幂等与退款异常处理**：Given 用户快速连点两次 `Receive`，Then 服务端仅发放 1 次奖励且前端不报错；Given 发生支付退款导致累计金额回退到档位线以下，Then 未领档位回退为 `Locked`（已领回滚口径按 `TBD-07` 确认后补充）。

## 10. 7 维对抗性边界审查报告（`prd-boundary-audit`）

### P0 逻辑矛盾或阻塞级缺口（必须确认后才能开发/定稿）

#### [P0-1] 示例中 `$1,434` 对应下一档 `$3,000` 与月充 `$1,500` 档位矛盾，且进度条起点未锁定
- **矛盾 / 缺失点**：原总结一方面写当前累计 `$1,434`、下一档 `$3,000`（进度条左侧 `$0`、右侧 `$3,000`、`47.8%`），另一方面又注明月充存在 `$1,500` 档位；同时未说明进度条左侧永远是 `$0` 还是“上一已解锁档位金额”（如 `$1,000` 到 `$1,500` 区间进度）。
- **极端触发场景**：如果后端存在 `$1,500` 档但进页面提示下一档 `$3,000`，用户再充 `$100` 会直接跳档，造成误导与客诉；若 `$0` 起算在高档位（如 `$10,000 → $30,000`）永远占前 33%，视觉反馈迟钝。
- **可选方案与推荐口径**：
  - 方案 A（推荐）：由服务端统一下发当前周期完整有序档位，并明确**进度条始终以 `$0` 为左端点**（与原总结公式 `min(current/next, 1)` 一致），当月充存在 `$1,500` 且 `$1,434 < $1,500` 时，`nextTierAmount` 必须返回 `$1,500`（差额 `$66`）。
  - 方案 B：若业务确认月充最低进度显示 `$1,500` 或按“上一档→下一档”分段百分比计算，则须重定义进度公式并在前端显示区间端点。

#### [P0-2] 支付退款 / 拒付后对“一笔充值同时计入三周期”与已领奖励的逆向回滚完全空白
- **矛盾 / 缺失点**：原总结定义了“一笔成功充值同时计入 Daily/Weekly/Monthly”，但未定义若该笔订单发生苹果/谷歌退款或支付风控拒付（Chargeback）时如何处理。
- **极端触发场景**：恶意用户充值 `$1,000` 后立刻领取 `Daily + Weekly + Monthly` 三个周期的 `VIP / 金币 / 靓号 / 首页曝光`，随后申请商店退款；若不回滚三周期累计额与资产，将被零成本刷穿高价值奖励。
- **可选方案与推荐口径**：
  - 方案 A（推荐）：退款/拒付成功后**实时等额扣减三周期未结束的累计 USD**，未领 `Available` 立即回退 `Locked`；自动发放未消耗的金币/道具自动收回，已消耗或人工曝光/靓号类触发**账号风控冻结 + 扣为负余额/取消活动资格**。
  - 方案 B：仅取消未来未领档位，不追缴已发奖励（风险极高，不建议用于 `$100–$30,000` 大额现金返利活动）。

#### [P0-3] “多个靓号模板仅能兑换一个”的作用域与“低档先领锁定高档”冲突
- **矛盾 / 缺失点**：`Rules` 声明不同档位获得多个靓号模板只能兑换一个，但未明确作用域（单周期内 / 跨 Daily+Weekly+Monthly / 整场活动），也未定义“低档先领之后，高档又解锁更好靓号模板时怎么处理”。
- **极端触发场景**：用户在 `$500` 档领了普通 `ABAB` 靓号模板并进入 `Pending Fulfillment`，月底冲到 `$10,000` 解锁稀缺 `AAAA` 模板却发现按钮被锁死不可换，引发大 R 用户强烈投诉。
- **可选方案与推荐口径**：
  - 方案 A（推荐）：明确作用域（建议**每个周期独立限兑 1 个**或明确整场活动仅 1 次），且若采用互斥锁定，在用户首次点击包含靓号模板档位的 `Receive` 前（或 `Rules` 中）明确“确认兑换此模板将占用本周期唯一靓号兑换名额”，或允许未完成 `Pending Fulfillment` 前联系运营升级替换。
  - 方案 B：只要在 `Pending Fulfillment` 前先不锁定，改为全周期结束后统一择优兑换 1 个。

### P1 重要边界缺失（建议补入 PRD 状态/异常矩阵）
- **[P1-1] 单档同时含“自动+人工”多奖励时的 `claimStatus` 颗粒度不足**：原 JSON 把 `claimStatus` 挂在 `tier` 级，若同档既有 `VIP Lv.3`（自动）又有 `Custom ID`（人工），点击 `Receive` 后状态标为 `Pending Fulfillment` 还是 `Claimed`？建议：保持外层主按钮为 `Pending Fulfillment` 不允许重复点击，**自动类奖励仍即时到账并在奖励行显示 `Auto Credited` 标记**。
- **[P1-2] 自然周期临界与跨零点订单归属 + 时区基准缺失**：建议锁定全平台统一结算时区（如 `UTC+0`），以**支付成功回调入账时间**归入周期；对于周期结束前已点击领取但处于 `Pending Fulfillment` 的人工奖励，周期重置后不得置为 `Expired`，须保留在运营履约台继续发放。
- **[P1-3] 周期进行中后台修改档位/下架奖励对在途用户的影响**：建议增加后台保护护栏——当前周期已有用户解锁/领奖记录时，**禁止修改已有档位金额与删档**；仅允许新增更高档位或配置到下一周期生效。

### P2 次要细节与一致性提醒
- **[P2-1] 跨币种充值换算展示与小数精度**：不同地区用户用本地货币充值时，进度条需统一按服务端结算汇率折算后的 `USD` 展示（建议明确保留整数还是 2 位小数，如 `$1,434` vs `$1,434.50`）。
- **[P2-2] 阿语 RTL 与超长英文多奖励行混排**：当单档包含 `2~4` 个奖励且遇到阿拉伯语 RTL 或超长礼物名时，卡片高度应支持自适应换行而非固定裁剪，右侧按钮保持固定宽度 `>= 44px` 垂直居中对齐。
