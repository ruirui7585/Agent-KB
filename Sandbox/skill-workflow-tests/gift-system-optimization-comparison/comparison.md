# 礼物系统优化：新旧 Skill 工作流对照

## 一句话结论

对这个已经拥有成熟 PRD 和两个可运行原型的真实需求，新工作流明显更合适：它先识别并复用现有资产，只补缺口；旧工作流固定重做 PM 分析、PRD、原型和 Review，结果更“厚”，但产生了大量重复内容。

## 实测结果

| 维度 | 旧工作流 | 新工作流 | 结论 |
| --- | --- | --- | --- |
| 路由 | 固定 PM → PRD → Prototype → Review | Discover → Align → Spec → Tickets → Execute → Review | 新流程先判断是否需要生成 |
| Token | 427,230 | 181,109 | 新流程少 246,121，下降 57.6% |
| 总耗时 | 18 分 46.9 秒 | 路由与补写约 7 分钟，另加快照及浏览器验证 | 新流程更短，但新流程计时不是统一 runner 的精确全程计时 |
| PRD | 新生成 38,191 bytes / 496 行 | 原样复用现有 17,324 bytes / 307 行 | 新流程避免第二份相互竞争的 PRD |
| 原型 | 新生成单页 60,885 bytes / 1,250 行 | 原样复用后台与公告原型，并携带 Axhub | 旧版视觉更完整；新版保留项目既有评审资产与注释能力 |
| 任务拆解 | 没有独立依赖图 | 6 个纵向 Ticket，含 blocking edges、验收和证据 | 新流程更利于分会话和并行 |
| 共识门槛 | 没有显式 gate | Sandbox 决策可继续，生产决策保留 TBD | 新流程减少把未知项写成事实的风险 |
| Review | 单份综合审查 | 需求、产品/UI、工程、证据四轴 | 新流程更容易区分“做错”和“证据不足” |
| 浏览器结果 | 页面可加载、无控制台错误；刷新后立即开面板受 loading 状态限制，重载后通过 | 两页可加载、无控制台错误；代表性导航、弹窗、切换、Toast 通过 | 两者均达到 Sandbox 可评审 |

## 质量差异

### 旧工作流的优势

- 从零开始时更直接：即使没有任何现成产物，也能固定生成一套完整交付。
- 新生成的单页原型视觉完成度更高，集中展示配置边界、状态、TBD 与移动端预览。
- 每一阶段都有独立 Agent 输出，适合需要强制“从头再想一遍”的场景。

### 旧工作流的问题

- 没先回答“现有 PRD 和原型是否已经足够”，因此把成熟资产全部重新生成。
- 产生第二套 PRD 和第二套原型，后续容易出现哪个才是事实源的问题。
- 四个阶段反复读取同一批项目上下文，Token 的主要浪费来自重复理解和重复创作。
- 没有显式 agreement gate、任务规模路由、纵向 Ticket 和证据状态。

### 新工作流的优势

- `route.json` 明确任务规模为 L，并先输出事实、复用判断、生成缺口与 gate 状态。
- `tickets.md` 把工作拆为 6 个纵向 Ticket，每个 Ticket 都有 outcome、non-goals、acceptance、evidence、blocked-by 和 open decisions。
- PRD、后台原型、公告原型均通过 SHA-256 证明为源文件原样快照，没有偷偷重写。
- 只新增真正缺失的产品分析与四轴 Review，因此 Token 下降 57.6%。
- 生产未知项继续保留为 TBD，不阻塞 Sandbox 对照，也不会被误写成生产规则。

### 新工作流的代价

- 路由本身仍消耗 107,025 tokens，说明 MVP 虽然有效，但 Discover 阶段仍偏重。
- 复用意味着新输出不会自动比现有原型更漂亮；它优化的是事实一致性和交付效率，不是视觉重做。
- 当前只是一次真实项目验证，不能据此断言所有项目都能节省 57.6%。

## 是否值得保留新工作流

值得。验证支持的不是“推翻旧 Skills”，而是增加一个轻量编排层：

1. 先判断任务规模和已有资产。
2. 达到当前交付物所需共识后再继续。
3. 只调用真正缺失的旧 Skill。
4. 用纵向 Ticket 管理执行边界。
5. 最后按四轴审查并记录证据状态。

旧 PM、PRD、原型、Review Skills 仍然保留，作为新工作流的专业能力模块；改变的是何时调用、调用几个、是否允许复用，而不是把原有能力删除。

## 下一轮最值得优化的点

1. 将 Discover 限制为“索引优先”：先读 README、目标 PRD、文件清单和变更摘要，只有发现缺口才展开长上下文。
2. 在 runner 中自动记录每阶段 token、时间、读文件数、复用字节数，避免人工汇总。
3. 给 `route.json` 增加 `reuse_hash`、`evidence_status` 和 `budget`，让复用和预算成为机器可校验契约。
4. 把浏览器代表性路径写入 Ticket，并由 runner 自动回填 pass/fail，而不是后置人工更新 Review。
5. 再选一个“只有想法、没有 PRD/原型”的 S/M 任务复测，确认新工作流在无法复用时不会比旧流程更慢。

## 实验边界

- 本结果只代表 2026-07-29 的一次 gpt-5.5 实测。
- 项目源目录、现有 Skill、Agent Manager 和知识库均未修改。
- 产物全部位于 `Sandbox/skill-workflow-tests/gift-system-optimization-comparison/`。
- 两套原型只完成代表性浏览器验证，不等同完整 QA 或生产验收。
