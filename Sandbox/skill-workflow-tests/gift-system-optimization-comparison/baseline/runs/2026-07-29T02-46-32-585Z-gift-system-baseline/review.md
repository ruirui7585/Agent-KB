# Laka 礼物系统配置优化 Review

> 状态：Draft review  
> 审阅对象：`input.md`、`pm-analysis.md`、`PRD.md`、`prototype/index.html`  
> 审阅角色：产品负责人、研发负责人、QA 负责人、数据审阅人  
> 说明：评分不是发布批准；当前稿件仍需补齐阻塞项后才能进入交付评审。

## 1. Overall Readiness Score

**72 / 100**

整体方向清晰，已覆盖输入要求中的核心拆分：保留礼物资源库，拆分 Tab、投放、角标、玩法、Banner，并明确不建设独立全服公告后台。PRD 对功能模块、状态、字段、异常、迁移、灰度、回滚、埋点和验收标准都有成体系表达；原型也能展示主要后台页面、前台公告和礼物面板草案。

扣分主要来自：多项上线关键规则仍为 `TBD`，部分 `TBD` 直接影响送礼是否允许、公告展示范围、隐私合规、缓存生效、灰度回切和客户端实现；PRD 缺少可执行的迁移验收和配置差异判定；原型偏信息展示，未充分体现真实校验、权限、审核、灰度、回滚和多语言/RTL 行为；埋点定义有事件表但缺少去重窗口、归因、失败枚举和看板验收。

## 3. Product Gaps

| Severity | Gap | Recommendation |
| --- | --- | --- |
| High | “全服”公告范围仍不清楚，是运营大区、国家、语言圈、全站在线用户还是房间生态范围。 | 将公告可达范围拆成业务定义、下发范围、过滤规则和客户端展示范围，并由业务方确认。 |
| High | “公告样式、队列、频控、有效期不可由运营编辑”已明确，但 PRD 又写入默认展示 5 秒，缺少来源和确认。 | 若 5 秒为客户端固定策略，需要标明来源；否则应回到 `TBD`。 |
| High | Banner 作为“礼物说明入口”的产品边界清楚，但缺少模板字段长度、阿语 RTL、图片安全区、备用素材、审核要求。 | 在 Banner 章节增加素材规格、语言长度、审核流、降级展示和验收截图要求。 |
| Medium | 礼物玩法与角标解耦后，允许“Lucky 玩法不选 Lucky 角标”仍为 `TBD`。 | 明确是否允许展示与能力不一致；若允许，增加强提示和发布二次确认。 |
| Medium | 礼物详情说明页只在字段中出现，缺少页面内容结构、入口、关闭、加载失败和多语言要求。 | 增补详情页信息架构和最小客户端状态。 |
| Medium | 后台发布流只描述“保存/发布/刷新缓存”，未明确草稿、审核、发布版本、操作日志、回滚版本之间关系。 | 增加发布状态机和版本生命周期。 |

## 4. Engineering Feasibility Risks

| Severity | Risk | Recommendation |
| --- | --- | --- |
| High | 数据模型中 `region_codes` 为数组，但公告事件协议只有单个 `region_code`，多大区配置如何生成公告不清楚。 | 明确配置维度到事件维度的展开规则，以及跨区去重。 |
| High | “一个 gift_id 仅一条生效玩法配置”可能无法覆盖同一礼物在不同场景/大区玩法不同的需求。 | 确认唯一性键是 `gift_id`，还是 `gift_id + scene + region`。这是高影响数据模型决策。 |
| High | 缓存、配置版本和聚合接口只概念描述，缺少读取路径、版本兼容、失效策略和客户端降级合同。 | 增补配置读取序列图、接口返回最小字段、版本兼容策略和缓存刷新 SLA。 |
| Medium | 公告事件缺少必填字段校验失败后的服务端错误码和丢弃枚举。 | 定义 `drop_reason`、`fail_reason`、`target_result` 枚举，供服务端、客户端、数据统一使用。 |
| Medium | 原型是单文件静态页面，交互没有真实数据校验、权限校验、筛选、发布版本或回滚模拟。 | 若用于研发评审，需要补充状态原型或在 PRD 中明确原型仅用于结构表达。 |

## 5. State, Permission, and Edge-Case Gaps

| Severity | Gap | Recommendation |
| --- | --- | --- |
| Blocker | 无发布权限、审核权限、停用被引用对象、强制停用的规则均未定。 | 确认角色矩阵、操作权限、审批要求、影响确认和审计日志字段。 |
| High | Tab、角标、Banner 删除规则均为 `TBD`，但状态矩阵包含删除流转。 | 删除能力上线前需明确软删/硬删、历史引用、恢复和审计。 |
| High | 礼物资源失效后的前端处理为 `TBD`。 | 明确已上架礼物资源被禁用、缺图、价格不可用、动画失败时的降级规则。 |
| High | 音乐礼物播放失败不回滚交易是合理方向，但播放范围、并发、静音和优先级未定。 | 音乐礼物应拆成独立决策项，不应与普通玩法一起进入开发。 |
| Medium | 客户端公告队列只定义同一时刻一条和过期丢弃，缺少多事件排序、最大队列长度、前后台切换、弱网重连规则。 | 增加公告客户端状态机。 |
| Medium | 多语言和 RTL 只写原则，缺少数字、用户名、金额、礼物名混排的验收样例。 | 增加英语和阿语样例截图/验收文本。 |

## 6. Analytics and Measurement Gaps

| Severity | Gap | Recommendation |
| --- | --- | --- |
| High | 埋点有事件名和属性，但缺少枚举定义，尤其 `fail_reason`、`drop_reason`、`target_result`。 | 建立事件字典，统一服务端、客户端、后台失败原因。 |
| High | 公告曝光分母使用 `gift_announcement_generated`，但事件是系统级，曝光是 viewer 级，分母粒度不一致。 | 定义公告可达用户数或下发用户数事件，否则曝光率会被低估或不可解释。 |
| High | 去重时间窗、跨设备去重、服务端/客户端归因均为 `TBD`。 | 上线前确定按账号、设备、会话或自然日去重。 |
| Medium | `gift_send_result` 涉及交易链路，若已有事件存在，新增或改名可能破坏历史口径。 | 先对齐现有埋点，不应默认新增替代交易主事件。 |
| Medium | 缺少实验/灰度监控指标，如新旧配置差异率、配置读取错误率、缓存版本命中率。 | 增加灰度看板必备指标和报警阈值。 |
| Low | Banner 只有曝光和点击，缺少详情页打开结果、加载失败和停留行为。 | 若 Banner 是重点教育入口，可补充详情页结果事件。 |

## 7. PRD-to-Prototype Inconsistencies

| Severity | Inconsistency | Evidence | Recommendation |
| --- | --- | --- | --- |
| High | PRD 要求覆盖迁移、灰度、缓存、回滚，但原型只有刷新缓存按钮和发布 toast。 | `prototype/index.html` 无迁移、灰度、回滚页面或关键状态。 | 增加灰度/回滚评审区，展示新旧配置对比、差异、回切入口和阻塞状态。 |
| High | PRD 的权限和审核流为重要开放项，原型没有角色、无权限、审核或审计日志表现。 | 原型所有主要操作均可点击或弹窗。 | 增加权限禁用态、发布审批状态和操作日志入口。 |
| Medium | PRD 数据模型支持多语言字段，但原型表单多为单语言输入。 | Tab、Badge、Banner 表单只有单个名称/标题输入。 | 原型应至少展示 EN/AR 多语言输入或缺失提示。 |
| Medium | PRD 规定投放页不维护玩法参数，原型符合；但表单中 `Operation label` 与角标/运营标签边界容易混淆。 | `form-placement` 有 Operation label，列表展示 badges。 | 增加解释：运营标签不等同前台角标，不进入 `badge_codes`。 |
| Medium | PRD 把私聊场景纳入范围，但前台原型几乎只展示语音房。 | Mobile Preview 是 Voice room。 | 增加私聊礼物面板差异或明确本原型只覆盖语音房主链路。 |
| Low | 输入要求产品文档中文，原型后台标签全英文。 | 原型侧栏、表格、表单均为英文。 | 如 Laka 后台实际使用中文运营标签，应改成中文后台文案；App 前台继续英文。 |

## 9. Recommended Next Actions

1. **Blocker**：召开产品/研发/QA/数据决策会，先确认 CP/Friend、Guardian、财富等级、音乐、全服范围、隐私替代、Lucky 金额口径这些会影响实现的数据和交易规则。
2. **Blocker**：补一版迁移规格，包含旧字段映射表、异常分组处理、角标去重规则、人工确认清单、新旧配置对比项和迁移验收标准。
3. **Blocker**：补一版灰度/缓存/回滚方案，明确配置版本、缓存刷新触发、灰度维度、差异阈值、报警负责人、回切权限和回滚粒度。
4. **High**：修订数据模型，确认 `gift_play_config` 唯一性键、`region_codes` 到公告 `region_code` 的展开规则、事件失败枚举和配置版本归因。
5. **High**：补齐权限和发布流，定义角色、审核、双人复核、强制停用、操作日志和影响确认。
6. **High**：补齐公告客户端状态机，包括队列排序、最大长度、过期、重复、前后台切换、弱网、权限失败、图片失败和 RTL 样例。
7. **Medium**：增强原型，增加迁移/灰度/回滚、权限、审核、多语言、私聊场景和真实阻塞校验状态。
8. **Medium**：完善埋点字典和监控看板，特别是 `drop_reason`、`fail_reason`、`target_result`、去重窗口、下发用户数和配置差异率。
9. **Low**：统一后台原型文案语言策略；若 Laka 后台实际为中文运营后台，后台原型建议改为中文，App 前台继续英文。
