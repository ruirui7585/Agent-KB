# Laka 礼物系统配置优化 PM 分析稿

> 状态：Draft  
> 来源：`input.md` 及 Laka 当前只读需求文件  
> 范围：仅做产品问题分析，不替代详细 PRD，不新增高影响业务规则

## 1. 问题陈述

### 已确认事实

- Laka 已有“礼物资源配置”和“礼物面板配置”。
- 礼物名称、价格、图标、动画等基础资源已由现有礼物资源库维护，本需求要求保留该资源库，不重复建设。
- 当前礼物面板配置同时承载分组、上架、展示时间、大区、角标、礼物类型、排序等职责。
- 当前“分组名称”实际承担前端 Tab 语义，但为自由文本录入，缺少独立 Tab 实体、稳定 ID、状态和排序管理。
- 新增或扩展 Lucky、全服、音乐、CP、Guardian、财富等级等礼物能力后，继续在面板投放记录中逐件维护玩法和角标，会带来配置重复、展示与能力不一致、修改成本高等问题。
- v0.6 方向要求：拆分礼物 Tab、礼物投放、角标、玩法、礼物说明 Banner；礼物与 Lucky 中奖公告保留在礼物玩法配置内，不建设独立全服公告后台。

### 推断

- 当前核心问题不是“缺少礼物资源”，而是礼物运营配置的数据职责混杂，导致后台难以支撑多玩法、多场景、多大区、多角标和前台公告扩展。
- 若不拆分配置职责，运营后续新增活动礼物、关系礼物或高价值公告礼物时，容易出现同一礼物在不同页面配置不一致、旧字段含义不清、客户端展示不可预期的问题。

## 2. 目标用户与场景

### 已确认事实

- Laka 是面向海外市场的陌生人社交产品，核心市场包括中东多个国家，用户为 18 周岁以上成年人。
- 礼物消费链路涉及运营后台、iOS、Android、服务端，以及语音房、1v1 私聊、亲密关系、财富等级、VIP、活动运营等模块。
- 当前需求关联页面包括礼物资源配置、礼物面板配置、礼物 Tab 配置、礼物角标配置、礼物玩法配置、礼物说明 Banner 配置和前台公告原型。

### 推断

| 用户/角色 | 主要场景 | 需要解决的问题 |
| --- | --- | --- |
| 运营配置人员 | 配置礼物 Tab、上架礼物、设置玩法、选择角标、配置 Banner | 降低重复配置，避免字段误用，提升发布可控性 |
| 后台管理员/审核人员 | 查看配置完整性、处理异常、发布或停用配置 | 需要清楚知道配置影响范围和异常原因 |
| 送礼用户 | 在语音房或私聊礼物面板选择并送出礼物 | 需要看到清晰分类、角标、说明 Banner 和可理解的玩法入口 |
| 收礼用户 | 在互动场景中收到礼物或关系类礼物 | 需要交易和互动结果稳定，不被公告服务异常影响 |
| 语音房在线用户 | 看到高价值礼物或 Lucky 中奖公告 | 需要公告不遮挡核心互动区域，并能点击进入事件房间 |
| 客户端/服务端研发 | 接入新配置、迁移旧配置、处理缓存和回滚 | 需要稳定数据边界、事件协议、降级与监控口径 |

## 3. 用户价值与业务目标

### 已确认事实

- 礼物系统与 Laka 的语音房、私聊、关系、等级、VIP 和活动运营相关。
- 男性用户是主要金币消费端，女性用户是主要社交供给端，礼物和虚拟资产是 Laka 商业模型的重要组成部分。
- 本需求不调整礼物价格、币种、结算、分成和 Lucky Gift 概率算法。

### 推断

- 用户价值：让用户在礼物面板中更容易理解礼物分类、玩法能力、角标含义和礼物说明，减少误解和无效点击。
- 运营价值：用稳定 Tab、玩法、角标和 Banner 配置替代自由文本和重复字段，提高礼物上新、活动投放和玩法维护效率。
- 业务目标：提升礼物消费链路的可运营性和可扩展性，为 Lucky、全服、音乐、关系类礼物和未来活动礼物提供更清晰的配置基础。
- 系统目标：减少配置职责冲突，降低配置错误导致的前端展示异常、公告误触发、缓存不一致和灰度回滚成本。

## 4. 范围与非目标

### 已确认范围

- 保留已有礼物资源库。
- 新增或重构礼物 Tab 配置，管理场景、大区、展示周期、默认 Tab、排序和状态。
- 礼物面板配置只负责把已有礼物投放到指定场景和 Tab，不再维护礼物基础信息和玩法参数。
- 新增礼物角标素材库，角标在礼物玩法中作为可复用标签多选引用，同一礼物支持多个角标。
- 礼物玩法配置维护单一主玩法、玩法附加条件、角标标签和 Banner 关联。
- 全服礼物按单次赠送金额门槛判断公告，幸运礼物按中奖金额门槛判断公告。
- 礼物说明 Banner 支持模板 Banner 和定制 Banner，点击后进入绑定礼物详情说明页。
- 提供礼物赠送和 Lucky 中奖两类前台公告线框及客户端展示逻辑。
- 覆盖迁移、灰度、缓存、回滚、埋点、异常和验收分析。

### 已确认非目标

- 不重建礼物基础资源库。
- 不调整礼物名称、价格、图标、动画、币种、结算、分成。
- 不调整 Lucky Gift 中奖概率、奖池或算法。
- 不建设通用平台公告后台。
- 不配置关系、用户等级、活动奖励等非礼物业务公告。
- 不允许运营编辑公告样式、文案、范围、跳转、队列、频控、有效期、隐私风控和兜底策略。
- 不直接修改当前线上后台或 App 页面。

### 推断的范围边界

- 本次更像“礼物运营配置平台重构”，不是单个礼物活动配置。
- 公告能力属于礼物玩法的结果展示，不应扩展为全平台公告运营能力。
- Banner 是礼物说明入口，不是送礼触发公告，也不是活动落地页系统。

## 5. 主要用户流程

### 运营配置流程

```text
确认已有礼物资源
→ 创建或维护礼物 Tab
→ 将礼物投放到指定场景、Tab、大区和展示周期
→ 上传或维护可复用角标素材
→ 为礼物配置单一主玩法
→ 根据玩法填写附加条件
→ 多选角标标签
→ 可选关联礼物说明 Banner
→ 校验配置完整性
→ 发布配置
→ 刷新缓存或等待配置生效
→ 灰度观察数据与异常
```

### 前台公告流程

```text
送礼或 Lucky 中奖成功
→ 服务端判断是否达到玩法金额门槛
→ 生成公告事件
→ 服务端下发给目标范围内在线用户
→ 客户端校验 event_id、event_type、expire_at 和必需字段
→ 客户端按本地语言渲染预置公告组件
→ 展示曝光埋点
→ 用户点击公告
→ 校验并进入事件房间，或提示房间已结束/无权限
```

## 6. 功能拆解

### 已确认能力拆解

| 模块 | 核心职责 | 关键边界 |
| --- | --- | --- |
| 礼物资源配置 | 维护礼物基础资源 | 本需求不改造，不复制资源字段 |
| 礼物 Tab 配置 | 管理礼物面板分类实体 | 替代自由文本分组，需稳定 ID、状态、排序 |
| 礼物面板配置 | 管理礼物在场景和 Tab 中的投放位置 | 只读展示玩法、角标和附加条件，不维护玩法 |
| 礼物角标配置 | 维护可复用角标素材库 | 通过角标编码被礼物玩法多选引用 |
| 礼物玩法配置 | 配置单一主玩法、附加条件、角标和 Banner 关联 | 不支持组合玩法，不生成自动角标 |
| 礼物说明 Banner 配置 | 维护模板/定制 Banner 内容与状态 | 礼物绑定关系在玩法配置中维护 |
| 前台公告组件 | 展示礼物赠送和 Lucky 中奖公告 | 样式、队列、频控、有效期、兜底不暴露给运营 |
| 迁移与灰度 | 将旧配置映射到新结构并支持对比 | 不回滚已完成送礼交易数据 |
| 数据埋点 | 衡量公告生成、曝光、点击、丢弃和 Banner 点击 | 需按 event_id、viewer_id 等口径去重 |

### 待 PRD 继续细化的功能点

- Tab 停用、默认 Tab 切换、无有效礼物时空状态的详细状态流转。
- 角标停用、删除、素材替换后的历史引用展示规则。
- 玩法类型切换后的字段清理、草稿保存和发布校验规则。
- Banner 停用、删除、模板复用、定制 Banner 独占绑定的异常处理。
- 客户端缓存刷新失败、服务端配置版本不一致、灰度命中差异的处理方式。

## 7. 成功指标

### 配置效率与质量

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| 礼物配置发布成功率 | 成功发布的礼物相关配置数 | 发起发布的礼物相关配置数 | 按配置类型、场景、大区拆分 |
| 配置校验拦截率 | 发布前被校验拦截的无效配置数 | 发起发布的礼物相关配置数 | 观察新校验是否有效发现问题 |
| 配置异常修复完成率 | 已修复并重新发布的异常配置数 | 被标记为异常的配置数 | 衡量后台异常提示可操作性 |
| 旧字段复用下降 | 新发布配置中仍依赖旧面板玩法/角标字段的配置数 | 新发布配置总数 | 目标应逐步归零，具体目标待定 |

### 前台公告效果

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| 公告曝光率 | 去重后的 `gift_announcement_impression` | `gift_announcement_generated` | 已确认口径：按 `event_id + viewer_id` 去重 |
| 公告点击率 | 去重后的 `gift_announcement_click` | 去重后的 `gift_announcement_impression` | 用于观察公告吸引力和跳转价值 |
| 公告丢弃率 | `gift_announcement_dropped` | `gift_announcement_generated` | 按 drop_reason 拆分频控、过期、风控、异常等 |
| 公告点击跳转成功率 | target_result=success 的点击数 | `gift_announcement_click` 总数 | 观察房间失效、无权限等问题 |

### 礼物说明 Banner

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| Banner 点击率 | `gift_banner_click` | Banner 曝光数 | 当前 PRD 已定义点击事件，曝光事件是否需要补充待确认 |
| Banner 配置完整率 | 完成必填内容并可发布的 Banner 数 | 创建的 Banner 数 | 按模板/定制类型拆分 |

### 业务影响指标

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| 礼物发送成功率 | 成功送礼请求数 | 发起送礼请求数 | 需保证配置改造不降低交易稳定性 |
| 礼物面板有效展示率 | 成功加载并展示有效礼物面板的会话数 | 打开礼物面板的会话数 | 可按语音房/私聊、大区、平台拆分 |
| 玩法礼物消费占比 | 指定玩法礼物成功消费金额或次数 | 全部礼物成功消费金额或次数 | 不涉及价格和分成规则，仅观察结构效果 |

## 8. 风险、依赖、假设与开放问题

### 风险

- 旧礼物面板字段与新 Tab/玩法/角标模型映射不完整，可能导致部分礼物投放丢失或展示位置变化。
- 自由文本分组迁移为稳定 Tab 后，历史同名、错别字、多语言分组可能需要人工确认。
- 玩法与角标解绑后，运营可能误以为选择角标会自动启用对应玩法，需要后台文案和校验降低误操作。
- 公告由玩法触发但样式和频控不在后台配置，运营可能需要清晰说明哪些内容不可运营编辑。
- 礼物公告涉及实时房间、队列、过期、风控和多语言渲染，客户端与服务端协议不一致会影响展示可靠性。
- 音乐礼物可能与语音房背景音乐、房主音频、用户静音设置产生冲突。
- Banner 模板和定制素材若缺少尺寸、字数、多语言与 RTL 规则，可能影响前台展示质量。
- 灰度期间新旧配置结果不一致时，需要明确切换和排查路径，避免影响线上送礼。

### 依赖

- 现有礼物资源配置的数据完整性，包括礼物 ID、多语言名称、价格、图标、动画等。
- 现有礼物面板配置、分组名称、角标、礼物类型和公告门槛等历史数据。
- 服务端礼物交易、Lucky 结算、公告事件生成、风控过滤、缓存和配置版本能力。
- iOS/Android 礼物面板、语音房公告、私聊礼物面板、RTL/多语言渲染能力。
- 运营后台权限、发布流、草稿/启停状态、审计日志和缓存刷新能力。
- 正式 Banner 视觉素材、礼物详情说明内容和前台展示组件。

### 当前假设

- 本次分析默认 v0.6 PRD 中未标注为待确认的内容可作为讨论稿基础事实，但仍不是最终上线规则。
- 礼物玩法中“一个礼物只配置一个主玩法”是当前 v0.6 方向。
- 公告只覆盖礼物赠送和 Lucky 中奖两类事件，不扩展到非礼物业务。
- 配置改造应优先保证交易链路稳定，公告或音乐等附加能力失败不应回滚已成功交易。

### 开放问题

#### 业务规则

- CP/Friend 礼物在双方无关系时，是禁止赠送，还是允许普通赠送但不增加关系值？
- Guardian 礼物在未建立守护关系时，是禁止赠送、降级普通礼物，还是提示建立关系后再赠送？
- 财富等级礼物的配置边界是什么：仅展示等级门槛，还是涉及消费后等级经验增长？
- 音乐礼物的播放范围、音量、并发优先级、打断策略和用户静音策略需要最终确认。

#### 价格、结算与资产

- 是否存在任何因玩法变更导致的价格、币种、结算、分成或返奖变化？当前要求是不调整，但需业务方确认不会产生隐性影响。
- Lucky Gift 中奖金额口径是否为最终结算金币，是否需要扣除失败项、退款或异常补偿？当前不能自行扩展。
- 定制 Banner 最终尺寸、文件大小、格式、动图支持范围和备用素材规则待确认。
- 礼物详情说明页是否支持视频，还是仅支持图文？

#### 权限与发布

- 哪些后台角色可以创建、编辑、发布、停用 Tab、角标、玩法和 Banner？
- 发布是否需要审核流、双人复核或操作日志？
- 停用被引用的 Tab、角标或 Banner 时，是否允许强制停用，还是必须先解除引用？

#### 合规、隐私与风控

- 公告中是否允许展示发送人、接收人、中奖人头像和昵称，及其在封禁、注销、隐私限制场景下的替代规则是什么？
- 不同国家、大区、语言环境下是否存在公告展示限制？
- 房间无权限进入时的具体权限提示文案和埋点分类待确认。

#### 迁移、缓存与回滚

- 旧分组名称到新 Tab 的映射规则和人工确认流程是什么？
- 历史角标素材去重规则、重复编码处理和失效素材处理规则是什么？
- 灰度期间新旧配置返回结果差异的可接受阈值、报警规则和回切负责人是谁？
- 配置缓存刷新是运营手动触发、发布后自动触发，还是客户端按版本拉取？
- 回滚是否仅回滚配置读取逻辑？已确认不能回滚送礼交易数据，但配置状态回滚粒度仍待明确。

#### 状态流转

- Tab、角标、玩法、Banner 的草稿、启用、停用、删除、失效状态是否统一？
- 玩法类型切换后旧条件字段清空是否可恢复？
- 已关联 Banner 被删除或停用后，前台是否立即隐藏，还是等缓存过期？

## 9. 结论

本需求的核心产品判断是：礼物系统应从“面板投放记录承载所有含义”调整为“资源、Tab、投放、角标、玩法、说明 Banner 分层配置”。这样可以保留现有礼物资源库，同时支撑 Lucky、全服、音乐、CP、Guardian 等玩法扩展，并避免把礼物公告误扩展为通用公告后台。

当前可进入详细 PRD/规格撰写，但必须继续保留 CP/Friend、Guardian、音乐优先级、Banner 限制与素材、礼物详情媒体、权限、迁移、缓存、回滚和合规隐私等开放问题，不应在无确认情况下写成最终业务规则。
