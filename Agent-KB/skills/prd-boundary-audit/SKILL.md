# PRD Boundary Audit

## 定位与原则

作为“防遗漏扫雷器”，在 `PRD.md` 定稿前（或高保真定稿前）专门排查**逻辑漏洞、互斥冲突与遗漏边界**。

- **只找漏洞、补边界、给推荐口径**，不推翻已确认的产品大方向，也不擅自将 `TBD` 写成既定事实。
- 适用于完整 `PRD.md`、拆分文档或结构化 `Feature Contract`。
- 不适用的维度必须显式标记 `N/A（不涉及原因）`，严禁静默跳过。

---

## 7 维对抗性检查清单

执行审查时，逐一用极端场景撞击文档规则：

1. **角色、权限与多端差异**
   - 谁可见入口、谁可点击操作？无权限时是隐藏、置灰还是点击提示？
   - 发生身份/资格变化（掉签、被拉黑、被踢、降级、封禁）时，进行中的状态怎么处置？
   - 消费侧 vs 供给侧、主态 vs 客态、iOS vs Android 是否分别覆盖？
2. **时序、时区与并发幂等**
   - 涉及“当日/周期/有效期/倒计时”时，时区基准（UTC vs 平台统一时区 vs 用户本地）是什么？
   - 跨零点订单（23:59 下单、00:01 结算）归哪一天？在途订单遇清零/过期如何归属？
   - 用户连点两次、弱网超时重试、多用户并发操作同一对象时如何保证幂等与展示一致？
3. **异常、中断与逆向回滚**
   - 余额不足、请求明确失败、请求结果未知（超时）时，前端状态是否会与服务端错位？
   - 发生退款、冲正、撤回或风控判定无效后，关联金币、钻石、亲密度、进度条、榜单及已发奖励是否级联回滚？跨日退款扣在哪一天？
4. **存量与运营配置级联**
   - 运营中途修改配置（改价、改门槛、停用、下架、过期）时，已生效的用户配置、进行中任务和历史快照按新规则还是旧规则？是否需要“存在进行中记录时禁止停用/删除”的后台护栏？
   - 老版本客户端看到新配置或新数据时如何降级？
5. **数据统计口径自洽性**
   - 进度计数源与数据统计源是否一致（避免“完成人数 > 付费用户数”导致完成率 >100%）？
   - 分子、分母、去重规则、分母为 0 兜底（展示 `0%` 还是 `—`）与多端拆分（iOS/Android）是否清晰无歧义？
6. **空态、极限值与多语言混排**
   - 0、负数、超大数字、空列表、满上限（如同时只能 1 个/最多 4 位且允许首位 `0`）是否定义？
   - 超长英文、阿拉伯语 RTL 混排、国旗与徽章并排时是否会遮挡或破坏布局？
7. **前后台字段与契约一致性**
   - 前台展示的参数是否都在后台字段表中有对应配置或明确写死？
   - 后台字段的默认值、取值上下限、生效时机（立即生效 vs 次日/下周期）与删除/停用提示是否闭环？

## 输出格式

```markdown
# 对抗性边界审查结果

## 总结速览
- 审查对象：<文档路径>
- 发现：P0 <N> 项 / P1 <N> 项 / P2 <N> 项（另 <N> 项维度为 N/A）

## P0 逻辑矛盾或阻塞级缺口（必须确认后才能开发/定稿）
### [P0-1] <问题标题>
- **矛盾 / 缺失点**：<指出原文哪里冲突或空白>
- **极端触发场景**：<用具体例子说明会出什么错>
- **可选方案与推荐口径**：
  - 方案 A（推荐）：<最低风险/最贴合当前架构的默认处理>
  - 方案 B：<替代做法及权衡>

## P1 重要边界缺失（建议补入 PRD 状态/异常矩阵）
- **[P1-1] <标题>**：<场景 + 推荐默认规则>

## P2 次要细节与一致性提醒
- **[P2-1] <标题>**：<建议>

## 已确认无漏洞 / 不适用维度（N/A）
- ✅ <已覆盖且自洽的规则>
- ➖ `N/A`：<明确不涉及的维度及原因>
```

---

## 禁止事项

1. 空泛评价（如“需要考虑异常情况”而不指明具体哪条规则、什么场景）；
2. 未指出依据就臆测业务数值或私自把推荐口径写成 `Confirmed`；
3. 为了凑问题数量把明确 `N/A` 的维度强行写成缺陷。
