# PM Delivery Workflow

## 定位与执行基线

作为唯一的产品原型流程编排器，控制阶段切换与修复闭环。执行准备检查内置于本 Skill，不调用独立的 `contract-review`；构建和审查分别委派 `ui-html-build` 与 `implementation-review`，不重复定义其内部细则。

```text
用户最新明确确认 > Feature Contract > 项目规范 > 已有旧逻辑 > Agent 默认判断
```

- 保留未被明确废弃的旧逻辑；用户确认与 Contract 冲突时先统一基线。
- 低风险假设可继续并在最终结果披露；关键业务规则严禁猜测。
- 每个阶段开始时只输出一句：`当前阶段：[阶段名称]｜预期产出：[一句话]`

---

## 执行流程

### 第一步：执行准备检查
只判断能否开始实现，不重议产品方案：
1. 输出目录明确可访问；优化已有项目时可定位目标页面和组件；
2. 修改范围与保持不变内容明确；
3. 角色、入口、核心流程、权限、状态、分支（所有改变可见 UI 或操作能力的分支）及验收标准可执行；
4. 目标终端、视觉来源、发布对象和目标访问地区明确；
5. Contract 内部无冲突，且不破坏未废弃旧逻辑。

输出结论：`go`（进入线框图）｜`go with assumptions`（按低风险假设继续并记录）｜`pause`（一次性提交待确认问题）。

### 第二步：静态线框图（调用 `ui-html-build` 阶段一）
- 在唯一 `index.html` 中静态展示全部计划页面及关键状态分支画板（不按低频/瞬时状态机械扩充；不同 UI 的角色/权限分支独立成板，不用文字替代画板）。
- 不生成业务动态交互；输出后等待用户确认，按反馈修改，明确确认后方可进入高保真阶段。

### 第三步：高保真静态原型（调用 `ui-html-build` 阶段二）
- 在同一个 `index.html` 原地升级为高保真静态原型与产品标注（不生成 `delivery.html` 或第二套展示 HTML，不新增 Contract 之外的产品规则）。

### 第四步：审查与修复（调用 `implementation-review`）
- 对照 Feature Contract 审查静态原型；明确偏差直接局部修复，只复查受影响范围和回归项。
- 同一问题最多修复 3 轮；超过 3 轮仍未通过则暂停并说明原因；审查通过前不得宣布完成。

### 第五步：自动部署与公网验证
`implementation-review` 通过即视为获得 Vercel 发布授权，默认直接部署 Production（不因新旧原型、首次发布或未绑定项目而询问）。遵循 [COMMON_UI_RULES.md](../../../COMMON_UI_RULES.md) 第 10 节“Vercel 公网整站只读”：

1. **部署前安全与绑定**：确认唯一入口 `index.html` 本地通过，整站修改型交互及写入入口均已在公网模式禁用（含仅浏览器临时生效的修改、URL 参数开关及写入接口），目录无密码/Token/私钥/敏感个人或内部数据；优先用已安装 `vercel`（否则 `npx --yes vercel@latest`，禁止全局安装），执行 `vercel whoami`（未登录则 `vercel login`），复用 `.vercel/project.json` 或执行 `vercel link --yes` 自动绑定。
2. **上传清单与发布**：执行 `vercel deploy --dry --format=json` 检查实际上传文件、数量和体积，用 `.vercelignore` 排除合同/内部文档/无关文件后再执行 `vercel deploy --prod --yes`（检查退出状态，失败则修复并重试最多 3 轮）。
3. **匿名与地区验证**：使用未登录状态访问部署 URL，验证页面非空、静态资源加载、无阻塞控制台错误、浏览/导航正常、全部修改型交互与写入接口不可用且与本地交付一致、未被 Deployment Protection 拦截，并确认目标访问地区可访问（无法验证时明确记为“目标地区访问未验证”，并在总状态标为“部分完成”）。

### 第六步：最终同步
以上五步全部通过后，一次性向用户同步结果。

---

## 验证职责分工与沟通规则

- `ui-html-build`：负责语法、资源、锚点、画布尺寸及基础页面自检。
- `implementation-review`：负责 Contract 覆盖、角色状态分支、标注层及视觉一致性审查。
- 第五步部署：仅检查上传清单、敏感内容、公网访问、整站只读与线上一致性，不重复下游检查。
- 正常流程仅在线框图完成后等待一次用户确认；自动修复不逐条打扰。

### 暂停条件与输出
触发暂停（Contract 无法兼容、缺少关键规则/目录、需推翻已确认规则或核心旧逻辑、含无法排除的敏感数据、Vercel 认证/绑定/发布超 3 轮失败、同一修复超 3 轮、不可逆风险）时一次性输出：
```text
阻塞问题：
不能自行决定的原因：
影响范围：
可选方案：
推荐方案：
需要用户确认的一个决定：
```

## 最终输出

```text
整体状态：完成 / 部分完成 / 阻塞

产品原型状态：通过 / 未通过
产品标注状态：本地编辑通过 / 公网评审通过 / 未通过
公网整站只读状态：通过 / 未通过 / 未验证
部署状态：成功 / 失败 / 未执行
目标地区访问状态：已验证 / 未验证 / 不可访问

最终文件：
- 本地唯一展示入口
- 标注数据及必要资源

审查结果：
- 是否通过
- 已修复问题

部署结果：
- Vercel 项目 / 部署环境：Production / 公网地址 / 访问范围：公开 / 受保护

验证结果：
- 本地实际完成的验证
- 公网实际完成的验证

假设与未验证项：
- 没有则写“无”
```

## 禁止事项

1. 调用独立 `contract-review` 或按复杂度拆分多套流程；
2. 跳过线框图确认直接做高保真，或跳过 `implementation-review` 直接部署；
3. 重复定义子 Skill 检查清单，或生成 `delivery.html` / 平行 HTML；
4. 只记录不修复、修复时重写整页、扩大需求范围或擅自改 Contract；
5. 自动全局安装 Vercel CLI、跳过 `--dry` 清单检查，或将获得 URL/匿名访问成功等同于目标地区访问已验证；
6. 声称完成未执行的验证，或隐藏未验证项/假设/遗留风险。
