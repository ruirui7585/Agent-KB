# PM Delivery Workflow

## 定位

作为唯一的产品原型流程编排器，负责控制阶段切换和修复闭环。

执行准备检查内置于本 Skill，不调用独立的 `contract-review`。具体构建和审查分别调用 `ui-html-build` 与 `implementation-review`，不重复定义其执行标准。

`implementation-review` 通过即视为获得 Vercel 发布授权。所有原型默认直接部署到 Production，不因原型新旧、是否已绑定 Vercel 项目或是否首次发布而询问用户。

## 执行基线

```text
用户最新明确确认 > Feature Contract > 项目规范 > 已有旧逻辑 > Agent 默认判断
```

- 以 Feature Contract 作为原型实现基线。
- 保留未被明确废弃的旧逻辑。
- 用户确认与 Contract 冲突时，先统一产品基线。
- 低风险假设可以继续，但必须在最终结果中说明。
- 不得猜测关键业务规则。

## 阶段告知

每个阶段开始时只输出一句：

```text
当前阶段：[阶段名称]｜预期产出：[一句话]
```

## 执行流程

### 第一步：执行准备检查

只判断能否开始实现，不重新讨论产品方案。

检查：

1. 目标输出目录是否明确、可访问；
2. 已有项目优化时，是否能定位相关页面和组件；
3. 修改范围与必须保持不变的内容是否明确；
4. 用户角色、入口、核心流程、权限、状态和验收标准是否可执行；
5. 所有会改变可见内容、按钮、入口或操作能力的角色、权限和状态分支是否明确；
6. 目标终端、视觉来源、发布对象和目标访问地区是否明确；
7. Feature Contract 内部是否冲突；
8. 新需求是否会破坏未标记废弃的旧逻辑。

输出：

```text
go：进入线框图阶段

go with assumptions：按低风险假设继续，并记录假设

pause：一次性提交需要用户确认的问题
```

### 第二步：静态线框图

调用 `ui-html-build` 的线框图阶段。

- 输出全部计划页面和状态的静态线框图。
- 每个产生不同 UI 的角色、权限或状态分支使用独立画板；文字或标注不得替代缺失画板。
- 不生成动态交互。
- 输出后等待用户确认。
- 用户要求调整时继续修改线框图。
- 用户明确确认后才能进入高保真阶段。

### 第三步：高保真静态原型

调用 `ui-html-build` 的高保真静态阶段。

- 基于已确认的线框图生成原型。
- 唯一展示入口为 `index.html`。
- 不生成 `delivery.html` 或第二套展示 HTML。
- 不增加 Feature Contract 外的产品规则。

### 第四步：审查与修复

调用 `implementation-review`。

- 对照 Feature Contract 审查静态原型。
- 明确偏差直接修复，不逐条等待用户确认。
- 修复后只复查受影响范围和必要回归项。
- 同一问题最多修复 3 轮。
- 3 轮仍未通过时暂停并说明原因。
- 审查通过前不得宣布完成。

### 第五步：自动部署与公网验证

仅在 `implementation-review` 通过后执行。

#### 1. 部署前检查

- 确认唯一入口 `index.html` 存在且本地验证通过；
- 检查待部署目录，不得包含密码、Token、私钥、真实个人信息、不应公开的内部业务数据或其他敏感内容；
- 确认发布对象和目标访问地区；默认继续自动公开发布，仅发现明确敏感或不应公开内容时暂停；
- 优先使用已安装的 `vercel`；未安装时使用 `npx --yes vercel@latest`，不得自动执行全局安装；
- 通过 `vercel whoami` 检查登录状态。未登录时启动 `vercel login`，仍无法完成认证则暂停；
- 已存在 `.vercel/project.json` 时复用当前项目；不存在时执行 `vercel link --yes` 自动创建并绑定项目，不询问用户。

#### 2. 上传清单检查

执行：

```text
vercel deploy --dry --format=json
```

- 检查实际上传的文件、目录、文件数量和体积；
- 发现合同、测试数据、内部文档或无关文件时，创建或更新 `.vercelignore` 后重新检查；
- 清单未确认安全前不得部署。

使用 `npx` 时，将以上命令中的 `vercel` 替换为 `npx --yes vercel@latest`。

#### 3. Production 部署

执行：

```text
vercel deploy --prod --yes
```

- 必须检查退出状态；
- 仅在退出状态为成功时记录命令返回的 Deployment URL；
- 部署失败时先修复明确问题并重试，同一问题最多 3 轮。

#### 4. 公网验证

部署成功后，使用未携带 Vercel 登录状态的请求或浏览器验证：

- URL 可以直接访问且返回成功状态；
- `index.html` 页面非空；
- 核心静态资源加载成功；
- 页面无阻塞性控制台错误；
- 线上内容与本次本地交付一致；
- 页面未被 Deployment Protection 阻止匿名访问。
- 目标访问地区可以实际访问；无法验证时必须单独记录为“目标地区访问未验证”。

只获得 URL 不等于部署完成。Vercel 匿名访问成功只代表部署成功，不代表所有目标地区均可访问。

### 验证职责

- `ui-html-build` 负责语法、资源、锚点、画布尺寸和基础页面自检；
- `implementation-review` 负责 Contract、角色分支、状态覆盖和视觉审查；
- 部署阶段只检查上传清单、敏感内容、公网访问和线上一致性；
- 不在多个阶段无目的地重复相同检查。

### 第六步：最终同步

满足以下条件后一次性同步结果：

- 执行准备检查通过；
- 线框图已获得用户确认；
- 高保真静态原型已生成；
- `implementation-review` 已通过；
- 明确问题已完成修复和复验；
- 唯一展示入口为 `index.html`；
- Vercel Production 部署成功；
- 公网地址已完成匿名访问验证；
- 目标访问地区已验证，或已将整体状态明确标记为“部分完成”；
- 假设、未验证项和遗留风险已如实记录。

## 用户沟通

- 正常流程只在线框图完成后等待一次用户确认。
- 自动修复过程中不逐条打扰用户。
- 不因新原型、首次部署、项目未绑定、Preview 或 Production 选择而询问；统一自动绑定并部署到 Production。
- 阻塞时一次性说明问题、影响、推荐方案和需要确认的决定。
- 完成后一次性同步最终结果。

## 暂停条件

仅在以下情况暂停：

1. Feature Contract 存在无法兼容的规则；
2. 缺少目标目录、必要文件或关键业务信息；
3. 必须改变已确认的产品规则；
4. 必须删除或覆盖未标记废弃的核心旧逻辑；
5. 同一问题经过 3 轮修复仍无法通过；
6. 部署目录包含无法自动排除的敏感数据；
7. Vercel 登录、权限或项目绑定无法自动完成；
8. Production 部署或公网验证经过 3 轮仍未通过；
9. 操作存在不可逆风险。

暂停时一次性输出：

```text
阻塞问题：
不能自行决定的原因：
影响范围：
可选方案：
推荐方案：
需要用户确认的一个决定：
```

## 最终输出

```text
整体状态：完成 / 部分完成 / 阻塞

产品原型状态：通过 / 未通过
产品标注状态：本地编辑通过 / 公网评审通过 / 未通过
部署状态：成功 / 失败 / 未执行
目标地区访问状态：已验证 / 未验证 / 不可访问

最终文件：
- 本地唯一展示入口
- 标注数据及必要资源

审查结果：
- 是否通过
- 已修复问题

部署结果：
- Vercel 项目
- 部署环境：Production
- 公网地址
- 访问范围：公开 / 受保护

验证结果：
- 本地实际完成的验证
- 公网实际完成的验证

假设与未验证项：
- 没有则写“无”
```

## 禁止事项

1. 对不同复杂度的新增需求拆分多套流程；
2. 调用独立的 `contract-review`；
3. 跳过线框图或线框确认；
4. 在线框确认前生成高保真原型；
5. 重复定义专项 Skill 的检查清单；
6. 生成 `delivery.html` 或第二套展示 HTML；
7. 页面生成后跳过 `implementation-review`；
8. 审查发现明确问题后只记录不修复；
9. 修复时重写整个原型或扩大需求范围；
10. 擅自修改 Feature Contract；
11. 声称完成了未实际执行的验证；
12. 隐藏未验证项、假设或遗留风险；
13. 在 `implementation-review` 通过前部署；
14. 自动全局安装 Vercel CLI；
15. 跳过上传清单或敏感数据检查；
16. 仅凭命令返回 URL 就声称公网可访问；
17. 部署失败或公网验证失败时仍宣布“完成”。
18. 将 Vercel 匿名访问成功等同于目标地区访问成功；
19. 因技术检查全部通过而忽略产品状态或权限分支遗漏。
